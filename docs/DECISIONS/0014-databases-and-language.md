# 0014 — Databases by placement, and eTamil as the default backend language

**Status:** accepted, 2026-10-26, recorded on the owner's instruction.
**Amended 2026-10-26:** the language rule is eTamil *by default*, with recorded
exceptions, replacing the first wording, which said *only*. Settles the edge
database left open in [0013](0013-edge-placement.md) and amends
[0011](0011-saas-architecture.md) on the export tool and the object-storage
client.

## Context

The owner's instruction: *let the local database be SQLite and the SaaS
PostgreSQL, but the backend language should always be eTamil, with no Python or
any other.*

The owner then refined it: eTamil should be the native choice everywhere it is
possible; a gap is filled by building the capability into eTamil; and a different
language is chosen only when that would be huge or complicated, as React is for
the front end.

## Decision

**1. Databases by placement.**

| Placement | Database |
|---|---|
| Edge, and the PoS terminal | **SQLite** |
| Cloud pool and cloud silo | **PostgreSQL** |

**2. eTamil is the default for every backend program nivaqi authors, wherever it
is possible.**

This covers server-side and operational code: routes, jobs, migrations, seeds,
sync, the updater, the tenant export tool, the object-storage client and the
tests. **When eTamil has a gap, the gap is filled by building the capability
into eTamil** — a change in `eTamil_lang` — **not by choosing another
language.** That is the project's research claim
(`eTamil_lang/docs/ARCHITECTURE.md`, the layering rule) applied to nivaqi.

**Another language is chosen only when building the capability in eTamil would
be huge or complicated.** Each exception is recorded here with its reason.
Three questions decide it:

1. Does it need something eTamil cannot express, such as durable storage,
   cryptographic primitives or rendering in a browser?
2. Is a mature, trusted component already available, where a mistake would be
   costly, such as a storage engine losing a ledger?
3. Do customers or auditors expect the standard component?

Recorded exceptions:

| Exception | Why |
|---|---|
| The React, Next.js and TypeScript front end, and its UI tests | Rendering in a browser. The owner's own example. The framework is in eTamil-ciRal ([0016](0016-front-end.md)) |
| SQLite and PostgreSQL | Storage engines. Durability, indexes, a planner, concurrency and recovery are the huge case, and file locking and fsync are Layer 0 |
| PgBouncer, a reverse proxy, Redis, LibreOffice (PDF conversion, through `கட்டளை_ஓட்டு`) | Infrastructure products nivaqi uses and does not write |

Using a third-party binary is fine; the exceptions are about code nivaqi
*authors*. Adding an exception is a decision recorded here, not a convenience
taken in passing.

## What it changes

**The tenant export tool is an eTamil program, not a `psql` script.** 0011 said
the opposite and is amended. Two constraints shape it:

- eTamil's driver takes parameterised queries only, and I found no bulk-copy
  statement.
- The interpreter refuses a second database in one process: it reports that the
  driver is "already connected" (`etamil_compiler/src/vm/interpreter.rs`, and
  `docs/ROADMAP.md` section 3). One process therefore cannot read PostgreSQL and
  write SQLite.

So export and import use **files as the exchange format**. One process reads
from one engine and writes JSON lines; another reads them and writes to the other
engine. `கோப்பு_எழுது` appends a line and `கோப்பு_சேமி` writes a whole file. How
fast this runs in eTamil is unmeasured.

**Sync between edge and cloud is HTTP between two eTamil processes** (`வலை_பதி`
out, `வழி` in), so no process ever holds both drivers.

**Migrations and seeds are eTamil programs**, run with `--vm` as
`aluvalakam_amYppu.qmz` is. `karuvi/` holds eTamil programs, not scripts in
another language.

**The kernel's SQL runs on both engines.** Modules use a common subset and
engine differences live in one place, the kernel. Known differences:

- Row-level security and `SET LOCAL` are PostgreSQL-only. The edge is one
  company and does not need them.
- Money representation: integer minor units on both engines, so the two
  engines agree (decision 0015).
- **UUIDv7.** PostgreSQL 18 has `uuidv7()`; SQLite has no equivalent, so
  identifiers (ARCHITECTURE section 6.4, rule 9) must be generated by eTamil on
  both engines. I found a clock that counts seconds (`இப்போதைய_நொடி`) but no
  general UUID or random-number builtin. The host links a UUID v4 generator and
  a random source for encryption; whether any builtin exposes them to programs I
  did not establish. UUIDv7 wants a millisecond timestamp and random bits.

**CI runs the kernel's tests against both engines.**

## Consequences

- The object-storage client for shared attachments (0011) is written in eTamil,
  not run as a sidecar.
- Two engines is a standing cost: two test targets, and a common subset of SQL.
- Any gap found while writing nivaqi becomes a request to `eTamil_lang`. That
  slows nivaqi when the gap is real and is the point of the rule.
- **Gaps found so far, to build into eTamil:** a UUID and random-number
  builtin, a millisecond clock, a currency-aware money library (0015), and
  possibly a decimal aggregate in the SQLite driver.

## Not taken

- **PostgreSQL on the edge:** heavier to run on a small machine, against the
  aim of minimum cost.
- **SQLite in the cloud:** one writer, and no row-level security.
- **A sidecar or script in another language** for export, sync or storage. None
  of these passes the exception test.

## Open

- **UUIDv7 generation:** a UUID and millisecond-clock builtin added to eTamil,
  which is the policy's answer, or composite `(tenant, id)` keys with
  per-device counters.
- **Development tooling in `eTamil_lang`, decided tool by tool with the exception
  test.** It is outside nivaqi's own code, but nivaqi's CI runs `check_names.py`.
  That script is 144 lines and is a port candidate. `generate_editor_support.py`
  is 1,655 lines and would need the test applied before any port. Not decided.
- **Export speed in eTamil** for large tenants. Unmeasured.
